# 背后灵推演「查了一堆卡却没结果」的四处修复

本改动是一次原子化提交，围绕一个真实对话场景展开：**创作者描述了一个完整局面要求复刻，AI 查了十几张卡、跑完工具，正文却停在半句话上，既没有结论，也没有提交可一键导入的战术步骤。**

复盘截图后发现四个独立成因叠在一起：① 单次回复上限被写死成8192，回答写不完被硬截断，而终止判定里没有「长度耗尽」这一项，于是这段半截正文被当成正常结果交给用户；② 规则引擎明明只是**没装**，工具返回的措辞却写成「校验异常」，模型据此认定「合法性不可信」，转而输出一段免责声明把结论吞掉；③ `get_card_info` 只接受单个卡密，多张卡只能逐张调用，来回十二次；④ 系统提示词没有约束模型不要先写「我先查一下」这类过程语，于是过程语被当成了正文。

修法上，输出上限这一项直接照搬了 ZCode 的处理方式，这也是本次改动里唯一一处需要先读外部代码才能做对的地方。

## 参考来源：三家对输出上限的处理

在决定「上限该给多少」之前，先去三个参考项目里查了它们怎么处理这件事，结果是三家有一个共同点：**都不猜**。

**ZCode 的做法最彻底**。它先把模型元数据里的输出上限读出来，读不到时**整个字段都不写进请求体**：

```ts
// ZCode/packages/services/src/model-provider/legacyZCodeConfigProviderReader.ts
const maxOutputTokens =
  readPositiveNumber(model.limit?.output) ??
  readPositiveNumber(model.options?.max_tokens) ??
  readPositiveNumber(model.maxOutputTokens)
// 早期 provider 配置可能只在 options.max_tokens 或顶层 maxOutputTokens 保存输出值。
// 读取时按 limit > options > 顶层兼容，写回仍收敛到标准 limit 结构。
const hasMaxOutputTokens = ... ?? maxOutputTokens !== undefined
return createModelProviderModelConfig({
  // ...
  maxOutputTokens: hasMaxOutputTokens ? maxOutputTokens : undefined
})
```

`undefined` 最终由 **JSON Merge Patch**落地——值为 `undefined` 的 key 根本不会出现在请求体里（**ZCode/packages/model-option-map/src/merge-patch.ts** 的 `mergeObject` 只写入 patch 中实际存在的键）。效果是：**不设上限时，厂商按自己的默认值走**，而不是我们替它猜一个数。

**opencode 的做法**是取模型真实上限与全局兜底值的较小者（**opencode/packages/opencode/src/provider/transform.ts**）：

```ts
export const OUTPUT_TOKEN_MAX = 32_000

export function maxOutputTokens(model: Provider.Model, outputTokenMax = OUTPUT_TOKEN_MAX): number {
  return Math.min(model.limit.output, outputTokenMax) || outputTokenMax
}
```

它的 `model.limit.output` 来自 **models.dev** 这个全网模型元数据库，所以能对号入座。兜底值 32000 比本项目原先的 8192 高出近三倍。

**DeepSeek Harness** 的做法是兼容多个元数据字段名（**deepseek-harness/packages/llm/llm-pi-ai/src/discovery.ts**）：

```ts
const maxTokens = capacity(
  entry?.maxOutputTokens,
  entry?.max_output_tokens,
  entry?.maxTokens,
  entry?.max_tokens,
  entry?.limit?.output,
  entry?.top_provider?.max_completion_tokens,
)
```

六个字段任一命中即可，明显是吃过「不同厂商元数据字段不统一」的亏；请求侧再逐级回退（**deepseek-harness/packages/llm/llm-deepseek/src/serialize.ts**）：

```ts
max_tokens: options.maxTokens ?? model?.maxTokens ?? connection.maxTokens,
```

对比之下，本项目原先的做法是把 `DEFAULT_MAX_TOKENS = 8_192` 无条件写进 models.json，既不知道模型真实上限是多少，也没有「不知道就不写」的出口——这就是为什么会撞上截断。

至于 Pi 本身，它已经天然支持省略：`@earendil-works/pi-ai` 的 `openai-completions` 适配层在构造请求时是`if (options?.maxTokens)` 才写字段（**node_modules/@earendil-works/pi-ai/dist/api/openai-completions.js** 第 588 行附近）。也就是说**只要 models.json 里不写 `maxTokens`，Pi 就不会把它传给厂商**，ZCode 那套机制在我们这边天然成立，不需要额外改造。

## 第一步：让「值不可知就不写」成立 —— **src/main/services/agentService.ts**

改动缘由：这是整个改动的地基。原先的写法是无条件回落到一个拍脑袋的常数，等于「不知道模型上限也照样告诉厂商一个数」，而这个数一旦偏小就会被硬截断。改成条件展开后，只有用户显式配置过才写这个字段；没配置就交给厂商自己的默认值。同时把兜底常数删掉——它已经不参与任何逻辑，留着会让人误以为还有默认值兜底。

## 第三步：把「引擎没装」和「战术不合法」彻底分开 —— **src/main/services/agentService.ts**

改动缘由：截图里模型说「ocgcore沙箱当前不可用，合法性以文本规则人工排雷」，随后就不再给结论了。这个行为是被我们的工具返回值诱导的——`getCore()` 抛错的原因是引擎未安装或路径不对，属于**环境未就绪**，但返回的文案是「ocgcore 校验异常」。模型读到「校验异常」就推断「引擎不可信，结论不可靠」，于是改输出免责声明。**工具的失败文案会被模型当作事实并据此改变行为**，所以措辞必须精确到能区分「环境问题」与「业务问题」。

```diff
         } catch (err: unknown) {
-          const errText = `ocgcore 校验异常: ${err instanceof Error ? err.message : String(err)}`
+          // getCore() 失败是**环境未就绪**（引擎未安装 / 路径不对 / 加载失败），
+          // 与「战术被规则判为不合法」是两件事。必须用不同措辞告知模型，
+          // 否则它会以为战术有问题，转而输出「引擎不可用，合法性以人工排雷」
```

## 第五步：在系统提示词里约束过程语与工具用法 —— **src/main/services/agentService.ts**

改动缘由：工具契约改完，剩下「模型把工作独白当正文输出」这一项只能靠提示词约束。沿用本项目既定的短 bullet 风格（此前系统提示词已按 Pi agent 的风格精简为「身份一句 + 几条规则」），补三条最紧要的：直接给结论、多卡批量查、工具报错不要中止。不要在这里写「请基于以上数据严谨分析」这类引导语——本项目一贯的取舍是**只给事实、让模型自己判断**。

```diff
   return `你是一个专业的《游戏王》卡牌决斗剧情创作者，你能调用工具查真实卡片数据、读取当前盘面、把推演步骤交给创作者。

   规则：
+  - 直接给结论，不要先写「我先查一下」「让我看看」这类过程说明。
+  - 需要查多张卡时，把卡密一次性传给 get_card_info；同一个工具不要重复调用同一个目标。
+  - 查不到或工具报错时，基于已有信息作答并说明不确定处，不要因此中止或只给免责声明。
   - 不要使用 emoji、表情符号和颜文字。
   - 战术推演完成后，调用 propose_duel_steps 把步骤交给创作者。${
```
