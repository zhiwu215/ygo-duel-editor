# 背后灵对话区重构：流式渲染、思考与工具展示

> 需求：创作者在背后灵里问一句「这场怎么打」，AI 会先思考一大段、再连着调十几次工具、最后才吐正文。旧界面把这三样都塞在一个带边框的助手气泡里：思考是一段默认折叠的等宽文本，工具是「执行中」+ 一个旋转的 Loader，正文每个 token 都要整段重新解析一遍 Markdown。长回复时界面发涩、发闪，而且**工具跑了一半、上下文被压缩这类「中间态」完全没有任何提示**，用户只会以为卡死了。
>
> 实现选择：只改渲染层，一个字节都不动引擎与工具协议（无头引擎的部分见 **docs/changes/无头引擎逐步对局：引擎当裁判与AI选择.md**，本次没有触碰）。参考仓库出处：**ZCode**（对话区 `packages/ui/src/v4` 的 reasoning / 工具块 / 错误横幅那一整套交互约定，以及 `styles.css` 的文案扫光）、**opencode**（`packages/session-ui` 的增量 Markdown 投影与 paced 节流思路）、**pi**（`@earendil-works/pi-coding-agent`，本次新接的上下文压缩事件源头）。

---

## 真实矛盾是什么

先说清楚要解决的到底是什么，后面的每一步都对应其中一条：

1. **每个 token 都在重渲染整个对话列表。** store 收到 `text_delta` 就 `messages.map()` 出一个新数组，面板里 `messages.map()` 直接内联渲染，于是第一条到最后一条全部重跑一遍 React 渲染 —— 对话越长越卡，跟「流式」本身没关系，是列表粒度错了。
2. **正文每个 token 重解析一次 Markdown。** `MarkdownContent` 没做 memo，内容一变就整段走一遍 `react-markdown` + `remark-gfm`。回复 5000 字、1000 个 delta，就是 500 万字符的重复解析。
3. **运行态全靠旋转图标。** 思考转圈、工具转圈、状态提示也转圈。ZCode 在源码注释里点破了这个坑：tool call 数量多且持续更新，旋转 loader 会长期占用渲染资源。一个十几步的对局推演，等于同时挂好几个永不停止的动画。
4. **思考块是「死」的。** 默认折叠，展开是纯文本（这点是对的），但折叠时除了「展开深度思考链」什么都没有 —— 用户看不出 AI 到底在想什么、想了多久。
5. **工具显示信息不够也不能查。** `duel_engine_*` 四个工具没有中文标签，直接显示英文原名；执行完只有一个截断的 `resultSummary`，没有「已执行/执行失败」的判定；参数与完整结果无处可看；多工具折叠后只知道总数，不知道有几个失败。
6. **布局与 ZCode 相反：** 助手消息也有气泡（`bg-card border shadow-xs`），正文被框在 95% 宽的盒子里；错误被拼进正文 `[发生错误: ...]`；没有复制入口。
7. **上下文压缩完全隐形。** Pi SDK 默认开着自动压缩（`DEFAULT_COMPACTION_SETTINGS = { enabled: true, reserveTokens: 16384, keepRecentTokens: 20000 }`），压缩期间没有任何正文和工具输出，界面干等。

## 第二步：正文不要再每个 token 解析一次 Markdown

**缘由**：矛盾 2。第一步之后只剩最后一条消息会重渲染，但它内部的 `MarkdownContent` 还是每 token 全量重解析。这里没有采用重工程化方案，而是两件小事叠加：`memo` 拦掉「props 没变」的渲染（历史消息、以及节流窗口内的重复渲染），再加一个节流钩子把解析频率压到 ~16 次/秒。

**参考**：opencode 的做法在 **opencode/packages/session-ui/src/components/markdown-stream.ts** —— 增量 block 投影，只重新解析最后一个未完成的 block，配合 `createPacedValue` 做 24ms 自适应的节奏化输出，重活还丢进了 **opencode/packages/session-ui/src/components/markdown-worker.ts**（Web Worker + latest-wins 队列）。它敢这么做是因为 SolidJS 的细粒度响应式可以直接改 DOM 节点。React 这边做不到「只更新最后一个 block」而不引入一整套自定义 reconciler，硬搬收益有限、风险很大。

**我怎么做**：只取它的「paced」思想，做一个纯时间节流。关键细节是**必须有 leading 补发** —— 朴素的「每次变化重设定时器」在 delta 间隔小于节流窗口时永远等不到触发，文本会整个冻住直到出现间隙。所以先算距上次刷新的间隔，够了就 `setTimeout(0)` 立刻补一帧，不够才排剩余的等待时间。

**src/renderer/src/components/BehindSpirit/usePacedText.ts**（新增）：

```diff
+export function usePacedText(
+  value: string,
+  active: boolean,
+  intervalMs = DEFAULT_INTERVAL_MS
+): string {
+  const [paced, setPaced] = useState(value)
+  const lastFlushRef = useRef(0)
+
+  useEffect(() => {
+    if (!active || value === paced) return
+    const elapsed = Date.now() - lastFlushRef.current
+    const timer = window.setTimeout(
+      () => {
+        lastFlushRef.current = Date.now()
+        setPaced(value)
+      },
+      elapsed >= intervalMs ? 0 : intervalMs - elapsed
+    )
+    return () => window.clearTimeout(timer)
+  }, [active, intervalMs, paced, value])
+
+  return active ? paced : value
+}
```

> 非流式时直接 `return value`，不做任何 state 往返：生成结束的那一帧必须拿到完整正文，不能停在节流窗口里的中间值上。

## 第三步：运行态统一改成「文案扫光」，去掉长期旋转的 Loader

**缘由**：矛盾 3。思考、工具、状态三处都在转圈。需要一个不占渲染资源的「进行中」表达，而且要在深浅两套主题下都看得见。

## 第四步：思考块要「活着」，但绝不能跑 Markdown

**缘由**：矛盾 4。折叠状态是思考块的常态（长思考展开会把对话撑爆），所以它必须在折叠时也能传达信息：AI 在想、想了多久、当前想到哪一句。

**参考**：**ZCode/packages/ui/src/components/ai-elements/reasoning.tsx**。它的几条约定我全部照搬：

- 折叠时不显示耗时，只显示一行流式摘要 —— 源码注释写得很直白：「收起态展示流式摘要，不需要为了隐藏的耗时每秒触发整块 reasoning 重渲染；展开时再按同一个开始时间补算并持续更新时间」。
- `BrainIcon` **不旋转**，运行态靠文案扫光表达（注释：thinking 会在长流式回复里持续存在，旋转 loader 会长期占用渲染资源）。
- 内容**强制纯文本**：`whitespace-pre-wrap`，注释给的理由正是性能 —— 「每次 chunk 都会重跑 Markdown 解析和插件渲染，字数越多越卡」。
- 收起后**延迟 300ms 才卸载**内容，因为 Radix 的高度动画在 closed 阶段还要读真实内容高度。

**我怎么做**：项目没有 Radix Collapsible，也不打算为一个动画引入它。改用 CSS grid 的 `grid-rows-[1fr] / [0fr]` 做高度过渡（Chromium 107+ 支持，Electron 39 完全够用），300ms 延迟卸载照做。摘要取思考文本的最后一行非空行 —— 和 ZCode 的 `resolveReasoningStreamingSummary` 同一个思路。

## 第五步：工具调用要有状态词、有分组统计、能展开查详情

**缘由**：矛盾 5。四个 `duel_engine_*` 工具直接显示英文原名；跑完只有一个截断摘要；失败和成功长得一样；多工具折叠只看得到总数。

**参考**：**ZCode/packages/ui/src/ToolCallBlocks/ToolLayout.tsx** 与 **ZCode/packages/ui/src/ToolCallBlocks/ToolSummaryRow.tsx**：

- 状态词一整套：等待中 / 执行中 / 已执行 / 执行失败 / 已拒绝 / 已停止。
- 失败态**不展开整块 JSON**，而是给状态词加 `underline decoration-dotted` 虚线下划线，错误详情挂 Tooltip（还带一个复制按钮）。
- 多工具分组头显示统计，ZCode 的措辞是「{count} 个命令，{count} 个失败」；运行中显示最新一条命令，完成态显示统计。
- 详情容器统一 `ml-2 border-border border-l pl-3.5`。

**我怎么做**：状态词按其语义收敛成四种（本项目没有「已拒绝」这种权限态，但拒绝信息会以 `resultSummary` 形式回来，走失败态）。两条与 ZCode 不同的现实约束：

1. **后端没有独立的工具错误字段。** `tool_call_end` 只有 `resultSummary`，失败也走同一个事件（`牌序编排被拒绝（...）`、`引擎开局失败: ...`、`引擎未就绪，已跳过`）。只能对摘要文本做启发式判定 —— 这是纯粹为了展示，不参与任何逻辑分支，误判代价仅是一行字显示成「执行失败」。
2. **项目没有 Tooltip 组件**（无 Radix）。退化成 `title` 属性，虚线下划线与 `cursor-help` 保留。

## 第七步：上下文压缩必须让用户看见

**缘由**：矛盾 7，也是这次最「隐形」的一个坑。翻 **node_modules/@earendil-works/pi-coding-agent/dist/core/compaction/compaction.js** 确认自动压缩默认就是开着的（`enabled: true, reserveTokens: 16384, keepRecentTokens: 20000`），也就是说**它一直在发生，只是没人看见**。压缩期间没有任何正文与工具输出，界面纯干等。

**参考**：事件契约来自 pi SDK 自己的类型声明 **node_modules/@earendil-works/pi-coding-agent/dist/core/agent-session.d.ts** —— `AgentSessionEvent` 里有 `compaction_start { reason }` 与 `compaction_end { reason, result, aborted, willRetry, errorMessage }`，`reason` 三选一 `manual | threshold | overflow`，`CompactionResult` 带 `tokensBefore` 与 `estimatedTokensAfter`。

**关键的一步是查清触发时机**，因为它决定事件该挂在哪条消息上：读 **node_modules/@earendil-works/pi-coding-agent/dist/core/agent-session.js**，`_runAutoCompaction` 有两个入口 —— `threshold` 走 `prepareRequest` / `_compactBeforeNextAssistantResponse`（即 `session.prompt()` 内部、**这一轮 assistant 请求之前**），`overflow` 走请求失败后的抢救路径。两种时机下渲染层都已经 push 了本轮的助手占位消息，所以事件能稳定挂上去。

**我怎么做**：新增一条 `context_compact` 事件贯通三层，UI 上做成一行和工具行同风格的提示：运行中「正在整理对话上下文…」（扫光），完成「已整理对话上下文 12.3k → 4.1k token」加一个「自动压缩 / 超限抢救」角标，失败/中断给虚线下划线 tooltip。

## 收尾：验证与遗留

- `npm run typecheck` 双端 0 错；改动文件 `eslint` 0 错 0 警；`electron-vite build` 通过。
- **未实机验证的两处**：一是流式长回复的卡顿是否真的消失（要一次几十步的对局推演才压得出来）；二是压缩提示——`threshold` 压缩要把对话堆到接近模型窗口才触发，建议用一个 `contextWindow` 较小的模型或长对话逼一次，确认「整理中 → 已整理 → 正文继续」的时序。
- 一个已知的工程约束：工具失败判定是**对 `resultSummary` 文本的启发式匹配**（`FAILURE_PATTERN`）。主进程目前只在 `tool_call_end` 上带一个摘要字段，没有独立的错误标志。要彻底解决得给事件加 `ok`/`error` 字段，但那要动二十余处 `tool_call_end` 发射点，本次没有扩大改动范围——展示层误判的最坏后果只是一行状态词显示成「执行失败」。
- 流式正文的「不完整 Markdown」（比如写了一半的表格或代码块）仍然会按完整语法渲染。真正的解法是 opencode 那种增量 block 投影或 ZCode 的 `streamdown`，都超出本次改动边界，留作后续。
