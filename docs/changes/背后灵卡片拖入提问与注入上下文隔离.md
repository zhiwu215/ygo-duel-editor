# 背后灵卡片拖入提问与注入上下文隔离

本改动是一次原子化提交，围绕一个诉求展开：**想把右侧「卡片检索」里的卡直接拖进背后灵输入框，就这张卡问 AI；而且拼给 AI 看的上下文不该出现在自己的对话记录里。**

这个需求在实现上撞到了两个真实的技术问题。第一个是数据通道：卡片检索面板本来已经支持拖拽（拖进决斗盘摆牌），拖拽载荷里带的是完整 `CdbCard`，所以理论上可以复用，不必新造通道。第二个要命得多——卡片是**结构化数据库记录**，不是文件。opencode 和 ZCode 的附件都是图片 / PDF / 代码文件，走的是「上传 → 模型侧读文件」，天然不会混进正文；而卡片必须序列化成文本才能塞进 prompt，一不小心就会把 `【我参考的卡片】…【我的问题】…` 这种拼接结果直接写进对话气泡。

动手前先去三个参考项目里查了同类做法，结论是 opencode 和 ZCode 都做了「发给模型的内容」与「展示给用户的内容」分离，但实现风格不同，详见下文「参考来源的核查与纠错」。

改动按「复用既有拖拽通道 → 定义展示与发送的分离契约 → 面板接入拖入与引用区 → 消息回看时的引用还原」的顺序推进。

## 参考来源的核查与纠错

最初凭一次 `grep synthetic` 就断言「只有 opencode 做了，ZCode 和 DeepSeek Harness 都没有」，这个结论是错的，用户当场质疑后重新核查，发现 ZCode 同样做了分离，只是字段名不同。两次核查结果如下。

**opencode 的做法**在 `opencode/packages/app/src/components/prompt-input/build-request-parts.ts`，它的返回值直接就是两份数据：

```ts
return {
  requestParts,      // 真正发给模型的（含注入上下文、附件、file part）
  optimisticParts,   // 渲染到对话记录里的
}
```

注入的上下文 part 会被标记 `synthetic: true`（同文件第 183 行），渲染层可据此隐藏；`opencode/packages/app/src/components/dialog-fork.tsx` 第 45 行取用户真实输入时明确排除：

```ts
const textPart = parts.find((x): x is SDKTextPart => x.type === "text" && !x.synthetic && !x.ignored)
```

**ZCode 的做法**在 `ZCode/packages/shared/src/zcode-task-types-core.ts` 第 950 行，用两个并列字段表达同一件事：

```ts
export interface ZCodeTaskSendPromptCommand extends ZCodeTaskRuntimeCommandBase {
  type: "send_prompt"
  content: string
  attachments?: ZCodePromptAttachment[]
}
```

`ZCodePromptAttachment` 是一个 discriminated union（image / audio / video / pdf / file），附件在**类型层面**就与 `content` 分离，结构上不可能被误拼进正文。它另有 `synthetic` 概念，但用于会话 fork 通知，与本场景无关——这正是第一次 grep 误判的原因。

**DeepSeek Harness 未核查**，不据此下任何结论。

这里得到两条对自己有用的经验。其一，断言「某项目没有 X」之前必须换多个关键词交叉验证，不能凭单次 grep 就下判断。其二，本项目场景比这三家都更难：它们的附件是文件，天然隔离；而卡片必须转成文本进 prompt，正是 opencode 那个 `synthetic` 标记所防的情形，所以 opencode 的思路对本项目更贴。ZCode 的 union 更严格但需要完整 part 模型，本项目用等价的轻量方案即可。

### 顺带厘清：optimisticParts 到底「乐观」什么

`buildRequestParts` 一次返回两份数据，其中 `optimisticParts` 这个名字容易被理解成「乐观的部分」，其实它乐观的不是内容，而是**「这条消息已经发出」这个状态**。查证下来它属于 UI 的一套「乐观更新」（Optimistic Update）模式：用户点发送后，立刻在本地 store 里插入这条消息而不等网络往返；请求真正发出去后，服务端返回权威数据再覆盖本地那份；失败则把这份本地数据撤掉。

`opencode/packages/app/src/components/prompt-input/submit.ts` 第 120 行同时拿到两份数据，第 144 行把 `optimisticParts` 写进本地 session store，第 147 行还配了一个 `remove()` 用于失败回滚——「先斩后奏、出错回滚」的语义就体现在这里。服务端数据到达时，`opencode/packages/app/src/context/server-session.ts` 第 1132 行的 `confirmOptimisticPart` 会用权威 part 把它替换掉，同时在第 388 行把已确认的部分挪进 `confirmedParts`。

所以三者的关系是：`requestParts` 是请求载荷（发给模型），`optimisticParts` 是同一批 part 补上 `sessionID` / `messageID` 后的本地副本（内容几乎不变，`build-request-parts.ts` 第 211 行是全量 `map`，只过了一遍 `toOptimisticPart`），而最终真相是服务端重新生成的权威版本。**`requestParts` 与 `optimisticParts` 的差别不是内容取舍，而是「给谁用」。**

这一点顺带修正了前文的一处措辞：先前把这两个字段直接概括为「展示 vs 发送」，作为本项目场景的类比是贴切的，但 opencode 原意的侧重点其实落在「本地先显示、等服务端确认」上，本项目并不需要这层——`sendMessage` 本身是 `await` 的，消息先落 store 再发请求，没有回滚场景需要处理。

真正值得借过来的是 `synthetic` 标记所解决的那个问题：`requestParts` 确实比用户输入多东西（注入的上下文就在其中），而 `optimisticParts` 忠实复制了这份多出来的内容，渲染层必须靠 `synthetic` 才能决定显示还是隐藏。最终本项目只借了这一半的思路，且在落地时有意做了差异——注入上下文只走 `injectedPrompt`，展示只用用户原文，而「引用了哪些卡」不隐藏而是折叠成一行标签。因为卡片是用户自己拖进来的，他当然知道引用了什么，完全隐藏反而是信息损失。

## 这次改动到底改变了什么

改动落地后回头确认一遍语义，有两处措辞值得说准，否则容易把机制理解偏。

首先是「注入了查询后的卡片信息」这一点是对的。拖拽载荷 `application/json` 里带的是完整 `CdbCard`，`buildPromptWithCards` 把它转成结构化文本交给模型——不是把卡密丢给 AI 让它自己去查。这样 AI 拿到的是 CDB 原文，准确、不漏字段，也不受它自身知识库的影响。

但「区分了输入的内容」这个说法需要修正。分流依据不是「输入的是卡片还是文字」，而是**同一句话的两个去处**。即使只拖了卡片、不打一个字，两个通道的内容也不一样：对话记录里是空的（因为 `prompt` 为空串），发给模型的是完整的卡片数据加一个空问题段。所以本质是按用途分流，不是按输入类型分流。

```ts
const buildPromptWithCards = (prompt: string, cards: CdbCard[]): string => {
  if (cards.length === 0) return prompt
  // ...
}
```

卡片与普通提问的判别是**隐式**的，就只有上面这一句早返回：拖了卡就拼，没拖就原样返回。效果上等价于「如果是卡片的话另走一条路」，但不依赖显式分支，这顺带保证了单人对局等无引用场景下行为完全不变。

最后一个细节是注入文本里**刻意不含任何引导语**。`【我参考的卡片】`、`【我的问题】` 只是分段标记，没有「请基于以上卡片分析」这类话。这与系统提示词的取舍是同一个道理——之前系统提示词被精简成「身份一句 + 几条 bullet」，就是照 Pi agent 的风格来的；同理这里也只给 AI 事实数据，判断让它自己做，效果描述是 CDB 原文，能不能用、怎么用都该由模型判断。
