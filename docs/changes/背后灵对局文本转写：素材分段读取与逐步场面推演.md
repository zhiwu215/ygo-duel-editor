# 背后灵对局文本转写：素材分段读取、步骤归一化与逐步场面推演

> 需求：创作者把一段 TXT / MD（小说章节，或随手写的一段对局，含几个流程与角色对话）交给背后灵，由 AI 自己分析原文、把乱序叙述重排成合规的对局顺序，然后能在决斗场上逐帧演示。
>
> 本文按**实际开发顺序**编排：每一步是一段思考，对应一份代码改动；代码一律用 diff 呈现。整个改动是一个原子化提交。实现过程中参考了项目根目录下的四个参考仓库：**pi**（PI Agent SDK 本体）、**opencode**、**ZCode**、**deepseek-harness**，参考点在每一步标注出处，文末附对照总表。

---

## 第一步：正文不进 prompt，素材用定位器传递

**缘由**：整章动辄数万字，直接拼进 prompt 有三个问题——挤占模型上下文、多轮对话反复携带同一份内容、正文污染对话记录（用户输入框里那点字和几万字素材混在一起）。

**参考**：deepseek-harness 的 prompt 分层设计（**deepseek-harness/docs/subsystems/system-prompt.md**）。它把系统提示分成有序注册的 `PromptSection`，动态易变内容（会话状态、进度）用 `PromptContext` 以 user 消息快照插在历史之后，明确「易变内容不进 system prompt、不进历史正文」以免污染 prompt cache。它的 `spill` 家族（**deepseek-harness/packages/spill/README.md**）则规定：超过 token 预算的完整结果存到会话私有文件，正文只保留一个定位器（locator）。本项目取「内容在主进程侧持有，传输层只带定位器」这一条：渲染端只传「哪本小说哪一章」的 id，主进程收到消息时经资料库服务读正文缓存，模型经工具分段读取。

## 第二步：给模型开一条分段读取素材的工具通路

**缘由**：主进程出于安全禁用了 Pi 默认的 read/bash 工具，模型原本没有任何读文件的途径；素材正文缓存进主进程后，需要一条受控的读取通路。全量吐回会一次性吃掉大量上下文，且模型容易只读开头就下结论。

**参考**：opencode 的读取与截断闭环（**opencode/packages/opencode/src/tool/read.ts** 与 **opencode/packages/opencode/src/tool/truncate.ts**）。opencode 的做法是：工具输出超过 2000 行 / 50KB 时**不丢弃**，把全文写到持久化目录并返回「预览 + 被截断说明 + 完整文件路径 + 建议的后续读取命令」，让模型能按 offset 继续取。deepseek-harness 的 `spill-policy` 用 token 预算把 head/tail 各留一半、正文替换为「预览 + 存储位置 + 用 grep/read 找回」的提示，且**存储失败时保底显示原文**（fail-open，绝不静默丢结果）。本项目把「分页 + 显式续读指引 + 读完显式宣告」吸收成无状态的 offset 分段读取。

## 第三步：步骤归一化层——模型写「召唤」「盖卡」也要能落地

**缘由**：转写小说时模型会写出中文动作词（「召唤」「盖卡」「攻击」）、大小写混排的阶段缩写（「m1」「bp.」），原 `propose_duel_steps` 的处理是直接 `as DuelActionType` 裸断言——垃圾值会**静默**写进台本，用户在界面上只看到一个不认识的动作标签。另外旧实现里「阶段写错」会被静默改成 M1，时序直接错位。

**参考**：

- ZCode 的失败语义（**ZCode/apps/zcode-cli/packages/core/src/tool/types.ts**）：`ToolHandlerFailure = { result: false, errorCode, message }`，业务校验失败用**返回值**表达而不是抛异常——模型看到失败原因可以自我修正，UI 侧 details 仍保留；
- opencode 的参数错误文案（**opencode/packages/opencode/src/tool/tool.ts**）：`InvalidArgumentsError` 的 message 直接写给模型看——"The X tool was called with invalid arguments: … Please rewrite the input so it satisfies the expected schema."——错误信息本身就是「请重写输入」的操作指引；
- ZCode 的「空输出也要占位」（**ZCode/apps/zcode-cli/packages/core/src/tool/executor/result-serialization.ts**）：空结果生成 `"(tool completed with no output)"` 防止模型把静默误读为成功。本项目把「绝不让模型读到无意义静默」反向用在归一化上：该报错报错、该降级附 note，不留中间态。

## 第四步：system prompt 的转写流程与分批防截断

**缘由**：原文档《背后灵推演无结果的四处修复》已经栽过一次「回复超长被截断、提案没来得及提交」的坑——转写任务步骤更多（二十多步），单次 tool call 参数超长必然撞上 `stopReason: 'length'`。必须把「分批」写进系统提示，并让工具返回值持续报累计进度。

**参考**：deepseek-harness 的 `guard` 家族（**deepseek-harness/packages/guard/README.md**）：`repeat-tool-reminder` 在模型重复完全相同调用时提醒换思路、`timeout-policy` 给超时一个明确语义。本项目吸收「防呆写进指令与返回值」的思路：system prompt 写清转写流程与分批要求，工具返回值提示「累计 N 步 / 已完成则不必再调」抑制重复提交。

**src/main/services/agentService.ts**（`buildSystemPrompt` 新增转写段）：

```diff
 - 用户只说「有一张盖卡」而没说是哪张时，code 传 0 并填 isUnknown: true，不要瞎猜卡名。
+- 创作者随消息附加了小说 / 文本素材（消息里会标注【小说素材】）并要求把其中的对局整理成可演示流程时：
+  - 素材正文不会出现在消息里，先用 read_novel_source 分段通读全文，读完再动手，不要只读开头就下结论。
+  - 转写的核心是排序：原文里的对话、插叙、解说和闪回不一定按对局顺序出现，必须按**决斗时间线**重排，归位到对应的回合与阶段；原文的叙述顺序不等于对局顺序。
+  - 先用 propose_board_setup 提交开局场面（clearExisting: true，含双方初始 LP 与手牌）；原文没交代的细节不要编造，模糊指代（如「一只怪兽」「不知名的盖卡」）用 isUnknown: true。

+  - LP 变动要跟住原文数值填进 lpChange；卡名或效果不确定时先 search_cards / get_card_info 查证，查无此卡就按模糊指代处理。
```

## 第五步：渲染端两条附加路径——拖入直接文本 + 文库选章

**缘由**：调研发现 `library:novel-*` 四件套后端早已就绪但渲染端零使用（有库无界面）；而用户的心智是「把文件直接丢给 AI」，强制走「进资料库 → 导入 → 选章节」不符合直觉。而且拿来的文本不一定有章节结构——可能就是随手写的一段对局，章节拆分对它没有意义。

**参考**：deepseek-harness `PromptContext` 的「缓存友好」原则再次适用——素材**正文**不进对话 prompt，气泡里只留标题与字数的展示面；同时 opencode 的「截断不是失败」体现在拖入过大文件时给出明确的、可操作的拒绝提示而不是崩溃或静默失败。

## 第六步：每步盘面快照——重放器让场面跟住时间线

**缘由**：实测转写一局后立刻撞上既有断点——AI 导入的步骤没有 `boardAfter` 快照，在台本里跳「下一步」时场面纹丝不动，只有时间线指针在走。用户的核心诉求就是「演示」，场面不动等于没做。无头规则引擎（ocgcore）接入局面输入是规划中的远期项，远水解不了近渴；而叙事级动作（召唤/盖放/送墓/抽卡）的位置语义是明确的、可确定性变换的，做一个轻量重放器就够演示用。

**参考**：这一步的机制起点是本项目自己的既有设计——`DuelStep.boardAfter` 轻量快照（**src/shared/types/story.ts**，注释明确「对标 MDPro3 对局动作与回放动作」）与 `previewStepBoard` 的整表还原。重放器是对这条既有回放链路的补全，而不是新造一套。对「解释不了的步骤」的处理参考了 opencode 截断哲学的延伸——**安静降级不崩溃**（沿用上一帧，不打 warning 噪音）；重放器生成的临时卡带专属 instanceId 前缀，避免与 store 的实例冲突。

## 第七步：确认流程按风险分级——汇总卡替换两张大卡

**缘由**：实测暴露的交互问题有三：布局与步骤分成两张卡、两个按钮，但「每个步骤对应一个场面」，二者本是一体，分开确认不合逻辑；二十多张逐条步骤大卡在气泡里把对话窗口撑爆；而「是否覆盖」的询问应该是**有条件**的——盘面是空的没有可破坏的东西，不该打扰；盘面上已有别人的布局才算破坏性动作。

**参考**：ZCode 的工具元数据（**ZCode/apps/zcode-cli/packages/core/src/tool/types.ts**）里的 `ToolMetadata`：`readOnly / destructive / riskLevel / needsApproval` 是工具声明的属性——**审批与否由动作的风险分级决定，而不是一律询问**。把这层思想搬到「应用提案」上：盘面空 = 只读直接放行；盘面有卡 = destructive，需要一次 `window.confirm`。至于「气泡里不展开全部内容」，对应 deepseek-harness 把易变过程状态留在事件流、不塞进长驻提示的取舍——过程细节在台本工作台里看，气泡只留摘要。
