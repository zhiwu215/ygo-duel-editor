# 模型能力元数据与输出预算

本文整理一次围绕「模型的上下文窗口与单次回复上限该怎么定」的长对话。起点是一个实测故障（AI 编排对局时被截断），中途拆到了四份参考源码（pi / opencode / ZCode / deepseek-harness）的元数据来源，最后落到本项目该写什么、不该写什么。

涉及的代码集中在 **src/shared/engine/agentModel.ts** 与 **src/main/services/agentService.ts** 两个文件。

## 起点的故障：正文一个字都没写出来

现象是引擎修好之后重跑同一道剧本，AI 连着调了 8 次 `get_card_info`（每批 10~12 张卡的完整效果文），然后报「回答因超出单次回复上限被截断」。日志里有一行最有信息量的字段：

```
chat WARN reply truncated by model length cap | streamChars=0 proposals=0
  hasBoardSetup=false hasCardSwap=false toolCalls=8 engineRunning=false elapsedMs=58318
```

`streamChars=0` 把问题定了性：它不是「正文写太长写不下」，而是**预算在正文开始之前就被工具参数吃光了**。

关键机制是——单次回复的输出 token 是**共享池**，由「思考链 + 正文 + 所有工具调用的参数」共分。8 次查卡的返回内容连同后续每轮的思考，把这个池子填满，轮到写正文时已无额度。

## 输出上限该填多少

### 为什么不能写死 8192

原代码是 `...(cfg.maxTokens ? { maxTokens: cfg.maxTokens } : { maxTokens: 8192 })`，注释里的理由是「deepseek-chat 硬上限就是 8192」。这是把**一个厂商的限制当成了全局默认**——声明 32K / 64K 窗口的模型也被无谓压回 8192，而编排任务（思考链 + 多次查卡 + 正文）在 8192 里必然截断。

四份参考源码的缺省值分别是：pi 16384、opencode 32000（`OUTPUT_TOKEN_MAX`）、ZCode 32000（`DEFAULT_NORMAL_REQUEST_MAX_OUTPUT_TOKENS`）、dsh 256000。本项目取 32768——比 pi 宽，与 opencode / ZCode 一致，且仍在主流厂商硬上限内。

### 关于「减去 4096」这件事

pi 的 `clampMaxTokensToContext`（**pi/packages/ai/src/api/simple-options.ts**）是这样的：

```ts
const CONTEXT_SAFETY_TOKENS = 4096
const MIN_MAX_TOKENS = 1

export function clampMaxTokensToContext(model: Model<Api>, context: TranscriptContext, maxTokens: number): number {
	if (model.contextWindow <= 0) return Math.max(MIN_MAX_TOKENS, maxTokens)
	const available = model.contextWindow - estimateContextTokens(context).tokens - CONTEXT_SAFETY_TOKENS
	return Math.min(maxTokens, Math.max(MIN_MAX_TOKENS, available))
}
```

这里的 4096 是「输出预算 нельзя把上下文顶爆」的缓冲：上下文窗口是**输入 + 输出共用的**，如果剩余窗口只剩 9000，却申请 32768 的输出，请求本身就不成立。

我早前举的例子是错的，写成了「剩下 11072 但设置 32768」却没有说明钳制后的结果。正确的读法是：

```
上下文窗口        131072
已用（含工具定义） 112000
减安全余量          4096
────────────────────────
剩余可用            14976
申请值              32768
最终生效 min(32768, 14976) = 14976
```

还有一点必须澄清：**clamp 本身治不了截断**。它只在「剩余窗口已经不够」时起作用；正文被工具吃光的情况，钳制出来的数字可能比原申请值还大，救不了场。

顺带补一个之前留下的疑问——pi 敢用一个固定的 4096，是因为它那个「已用 context」是**包含工具定义**的。`estimateContextTokens` 走 `normalizeContext()`（**pi/packages/ai/src/utils/transcript.ts**）把 systemPrompt 与 tools 折成一条 leading system message，而 `estimateMessageTokens`（**pi/packages/ai/src/utils/estimate.ts**）对 `toolsAdded` / `toolsRemoved` 明确算 token，并且优先采信上一次 assistant 的真实 usage。所以它的余量口径比「只算对话」更保守。

### 「模型声明的值优先」到底指什么

我之前说过一句容易误导的话：**「模型声明了更大的就该原样用」**。你追问过「我给模型声明了一个更大的上限，但是模型不支持，所以模型用它自己的吗」，这个追问是对的，我当时的表述不准确。

四份参考里的「声明值优先」，指的是它们**内置的模型能力元数据表**（记着每个模型的 context / output 上限）比硬编码缺省值权威。**不是**指用户手填的配置能突破服务端。

真实行为是：配置里填的值就是我们**请求**的值；服务端硬上限更低时，它会**拒绝**这个请求（报参数错误），而**不会**静默钳到自己的上限替我们兜底。所以正确的心智模型是：

- 填小了 → 白受限制（这是我们之前写死 8192 的病）
- 填大了 → 请求被拒，报错
- 只有填对了才正常工作

### 上下文窗口误填的连带效应

这个耦合点值得单独记一笔：`resolveMaxTokens()` 用 `contextWindow` 去钳 `maxTokens`。所以如果把上下文窗口填小（例如误填 16384），输出上限会被连带钳到 `16384 - 4096 = 12288`，白丢额度。两个字段虽然并排放在设置里，但存在这个隐含依赖。

## 卡的效果文不能截断

截断问题暴露后，我给出的方案是给 `get_card_info` 加一个「本轮累计 16000 字符」的闸门，超限后只回一句「你已经有足够信息了，请动手」。你直接指出了这个设计的根本错误：

> 假如说字符到达了上限，查询的卡片就不能让 AI 获得整个效果了吗？但是那样的话，AI 就不好推断卡片之间的联动了呀，毕竟效果都不知道了。

你是对的，而且理由比「不方便」更硬。效果文里的两类记号是**规则语义**，不是排版噪声：

- `①②③` 是**效果编号**。其他卡的效果文本里会写「这个效果①……」，跨卡引用就靠它。丢掉编号，「这张卡能不能被那张卡检索 / 无效 / 复制」就没有依据。
- `●` 是**发动条件标记**。像「●自己场上有龙族怪兽存在的场合」这类分支，`●` 是分支的起点。丢掉之后一串并列条件会糊成一段话。

所以那道闸拦下的不是浪费，是必要的推理材料。我也撤回了更早提过的「压缩效果文换行、剥离记号」的建议——那同样是错的。

### 换成一次性注入的账怎么算

不算不知道，这道闸在数学上就是错的。整副卡组约 40 张，双方合计约 87 张；单张卡含完整效果文约 400~600 字符：

```
87 张 × 约 520 字符 ≈ 4.5 万字符 ≈ 1.2 万 token
```

这个量级：相对 32768 的输出上限，它是一次性的工具结果，不是每轮重付；相对 131072 的默认上下文，不到 10%。而它换来的是**整场对局中模型手里始终有全部卡的完整文本**。

也就是说，「按字符限流」是在用**不确定的多次小额成本**，去规避**一次确定的 1.2 万 token 成本**——算错了方向。

现行做法（**src/main/services/agentService.ts**）：`duel_engine_start` 成功时调用 `buildCardTableText(state)`，把双方全部卡片的**完整** `desc`（不截断）一次性拼进工具结果，并发散注入的卡密记进 `injectedCardCodes`；此后 `get_card_info` 对已注入的卡只回一行「开局已完整给出，不再重复」，**没注入过的新卡照样返回全文**。

关键差别在于：**闸门是「不给你更多」，去重是「不给你重复的」**。前者断推理材料，后者才是真的省。

实现时踩到一个坑值得记：`FieldCard` 的卡密字段是 **`code`**，不是 `id`（`id` 是 `CdbCard` 的数据库主键，也等价于卡密）。第一次按 `card.id` 取直接报 `TS2339`。

## RAG 在这个规模下是过度设计

你问过是不是该上扫描中间件、框架，比如 RAG。答案是不该，理由是**素材总量太小**：整局卡表就是 87 张卡、4.5 万字符。RAG 要解决的是「语料远超上下文窗口、只能靠检索挑一部分进来」的问题。这里全部装得下，且装进去之后模型永远看到全貌——这正是推理卡间联动需要的。上 RAG 反而会把「完整」退化成「检索到的那几张」，重蹈字符闸的覆辙。

## 元数据是从哪来的

你问了两层：这些数据从哪来、我能不能用。

四份参考的元数据**最终都源自 models.dev**：

- **pi** 是源头。`packages/ai/scripts/generate-models.ts` 里一行 `await fetch("https://models.dev/api.json")`，字段映射非常死板——`contextWindow: m.limit?.context || 4096`、`maxTokens: m.limit?.output || 4096`，每一处都一样。除 models.dev 外还抓 openrouter、Vercel AI Gateway、NVIDIA NIM，四源合并时 **models.dev 优先**。
- **opencode** 自建镜像，抓 `models.opencode.ai/api.json`。
- **ZCode** 手写一份约 187KB 的规则 JSON（`zcode-builtin.json`），用正则匹配推断。
- **deepseek-harness** 直接依赖 pi 的包，自己不做。

所以「我可以使用吗」的答案是：**可以用，但对你的模型没用**。因为 models.dev 只收录**厂商官方模型 id**。我实际查过 pi 的生成脚本：DeepSeek 那两条（`deepseek-flash` / `deepseek-v4-pro`）根本不在 models.dev 抓取范围里，而是在脚本里**手写常量**，带着 `contextWindow: 1000000, maxTokens: 384000` 和手写的 `thinkingLevelMap`。`zai`、`ant-ling`、`opencode` 同理。

models.dev 的 DeepSeek 只有 `deepseek-chat` / `deepseek-reasoner` 这两个官方 id。你在设置里填的 `deepseek-flash` / `deepseek-v4-pro` 在那边查不到——**即便接上 models.dev 也匹配不上**。

## pi 的四层是怎么搭的

你问「A + B 结合，pi agent 是如何实现的」。答案是它做了**四层**，而且「B 那层（随包发布的快照）」是代码生成出来的，不是手写的。

### 上游数据源

`generate-models.ts` 在构建期抓 models.dev、OpenRouter、Vercel AI Gateway、NVIDIA NIM 四个源。这一层不属于 pi，是别人的接口。

### 构建期快照

同一个脚本把抓来的结果序列化成 JSON 分片 + TS 类型，写回包里：

```
src/providers/data/<provider>.json        数据，每个供应商一片
src/providers/<provider>.models.ts        类型包装，flattenChatModelCatalog
src/models.generated.ts                   聚合入口
src/providers/data/manifest.json          generatedAt 时间戳
```

`deepseek.models.ts` 全文只有 8 行，就是个 wrapper。这一步的产物**跟着 npm 包发出去**，所以任何用户装上 pi 就立刻有全套元数据，**不需要联网**。

`manifest.json` 里的 `generatedAt` 会在运行期被 `getBuiltinModelDataGeneratedAt()`（**pi/packages/ai/src/providers/all.ts**）读出来，作用是判断「远端目录是不是比我的内置快照更新」。

### 发布目录

`publish-model-catalog.mjs` 把产物推到对象存储，路径带 **revision = sha256**：

```
models/v1/index.json
models/v1/revisions/<sha256>/providers/deepseek.all.json
```

`index.json` 维护 `minimumPiVersion → revision` 的映射表（协议定义在 **pi/scripts/model-catalog-protocol.ts**），客户端按 semver 选出「我这个版本支持的最新 revision」。整棵树按 `/api/models/providers/<id>?types=chat,image,classifier` 对外提供，带标准 `ETag` / `Last-Modified`，revision 目录用 `Cache-Control: immutable` 永久缓存。

### 运行期覆盖

这层是真正对应「A 方案」的部分。`withRemoteCatalog()`（**pi/packages/coding-agent/src/core/remote-catalog-provider.ts**）挂在 provider 的 `refreshModels` 上，逻辑相当谨慎：

- 每 4 小时（`REMOTE_CATALOG_REFRESH_INTERVAL_MS`）才真正发一次请求；
- 只有本地已经存有完整 body 时才带 `If-None-Match`——注释写明「a 304 can never leave the overlay empty」，防止 304 把覆盖层清空；
- 304 → 只更新 `checkedAt`；404 / 501 → 记 `lastModified: 0`；网络抖动 → 保留旧 etag，下次再试；
- 单次尝试超时 4 秒，并且 abort 后不再写入。

持久化在 `FileModelsStore`（**pi/packages/coding-agent/src/core/models-store.ts**），落盘 `models-store.json`，条目形如 `{ models, etag, lastModified, checkedAt }`。

防倒车的判据在这里：

```ts
function remoteModels(entry, localGeneratedAt) {
	if (!entry) return []
	if (localGeneratedAt !== undefined && (entry.lastModified === undefined || entry.lastModified <= localGeneratedAt)) {
		return []
	}
	return entry.models
}
```

远端目录比内置快照还旧，干脆不用。

最后合并的时候是 **内置快照作底 → 远端目录覆盖 → 用户手填再盖一层**（`model-runtime.ts` 里 `mergeModels`，按 `<type>\0<id>` 为键）。

## 本项目实际写的是什么

结论：**四层里只需要第二层，而且第二层只能手写。**

第三层（发布目录）与第四层（ETag 增量刷新）解决的是 pi 的问题——几十个供应商、几百个模型、装好的客户端要能热更新，而团队不想为每个新模型发一次包。本项目情况完全相反：供应商由用户自己添加，模型 id 由用户自己填，要更新的内容只是**两个数字**。为两个数字建一套版本协商 + 增量刷新，是纯粹的负债。

第一层也接不上——models.dev 里没有你的模型 id。

所以实际实现落在 **src/shared/engine/agentModel.ts**：

```ts
export const AGENT_MODEL_CAPABILITIES: Record<string, { contextWindow?: number; maxTokens?: number }> = {
  'deepseek-flash': { contextWindow: 1_000_000, maxTokens: 384_000 },
  'deepseek-v4-pro': { contextWindow: 1_000_000, maxTokens: 384_000 },
  'qwen-plus': { contextWindow: 131_072, maxTokens: 32_768 },
  'qwen-max': { contextWindow: 131_072, maxTokens: 32_768 },
  'moonshot-v1-128k': { contextWindow: 131_072, maxTokens: 16_384 },
  'glm-4-plus': { contextWindow: 131_072, maxTokens: 16_384 },
  'abab6.5s-chat': { contextWindow: 262_144, maxTokens: 16_384 }
}
```

然后在 `resolveActiveRuntime` 里做**三层回退**：

```ts
const builtin = AGENT_MODEL_CAPABILITIES[model?.id ?? '']

return {
  contextWindow: model?.contextWindow ?? builtin?.contextWindow ?? config.contextWindow,
  maxTokens: model?.maxTokens ?? builtin?.maxTokens ?? config.maxTokens
}
```

**用户为该模型手填的值 → 内置能力表 → 全局缺省。**

这张表排在手填之后，与 pi 的次序相反（pi 是内置表优先）。理由是本项目的表是手写的、只对官方端点有把握；用户把它指向第三方中转时（同一个 id、上限常常不同），必须听用户的。

这是「手写补丁」而不是妥协：pi 自己面对 models.dev 覆盖不到的模型时，解法也正是在生成脚本里手写常量。**手写是这个规模下的正确答案。**

至于什么时候才该上 pi 那套完整分层，需要同时满足三条：内置一份固定的官方模型清单（不是让用户填）、供应商数量到两位数且会变、模型 id 会被厂商改名下架而你需要不发版就纠正。目前一条都不满足。

## 顺带改掉的两处文案

**Settings 里的模型举例**。帮助文案原先写着「部分厂商硬上限较低（如 deepseek-chat 为 8192），填超过会被服务端拒绝」。你的反应是「为什么还有 DeepSeek chat 这个模型的事情，我这里根本就没有啊」——举一个用户根本没在用的模型只会造成困惑。已改为「填超过模型本身支持的上限会被服务端拒绝」（**src/renderer/src/components/Settings/AgentSettingsContent.tsx**）。

**文档里的措辞**。「模型声明了更大的就该原样用」这句已按上文「『模型声明的值优先』到底指什么」一节更正，见 **docs/changes/无头引擎逐步对局：引擎当裁判与AI选择.md** 增补十。

## 验收与遗留

`npx tsc -p tsconfig.node.json --composite false --noEmit` 与 `-p tsconfig.web.json` 均零错误；`npx eslint` 对改动文件零警告；prettier 检查通过。

解析逻辑实算：缺省 → 32768；用户配 8192 → 8192（原样生效）；上下文误配成 16384 时 → 输出上限被钳到 12288。

遗留一项：尚未在 Electron 中人工跑一遍，确认卡表注入后的实际上下文占用与模型行为。复验方式是重启 dev 跑同一道剧本，看 `duel_engine_start` 的结果尾部有没有「本局双方卡表（完整效果文，已一次性给出）」段落，以及 `agent.log` 截断行是否带上 `injectedCards` 字段。
